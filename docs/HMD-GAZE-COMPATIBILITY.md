# Eye-tracking headset compatibility audit (2026-10-26)

This document separates three different claims: (1) headset eye data exists, (2) a Windows side process can read it while PC VRChat runs, and (3) this project's NVIDIA VRSS2 provider is accepted and moves the high-quality region correctly. The maintainer confirmed all three on Pimax Dream Air; a contributor separately reported VRChat tracking on Steam Frame / NVIDIA 596.02. Other routes still need in-headset validation. A working VRCFaceTracking avatar or foveated **stream encoding** does not prove VRSS2 rendering.

Face-tracking software coexistence and known port/SDK ownership risks are audited separately in [FACE-TRACKING-COEXISTENCE.md](FACE-TRACKING-COEXISTENCE.md).

## Wireless priorities

Wireless transport is not a blocker by itself. Quest Pro with Steam Link exposes a PC OpenVR eye action. The generic bridge takes its combined gaze target in SteamVR standing coordinates, transforms it through the current HMD pose and each eye's projection/translation, and stops output when gaze or HMD pose is invalid. This conversion passed synthetic tests, not a live Quest Pro test. The dedicated Steam Frame session instead reads OpenVR's foveation-center API and uses a Frame-specific registration identity on the audited NVIDIA 596.02 build; see [Steam Frame](STEAM-FRAME.md). Galaxy XR already has a practical PC eye-data path through Virtual Desktop/VRCFT, but that path is a different adapter; headset-side Android XR permissions alone do not deliver samples to this Windows program.

Steam Frame and recent Virtual Desktop builds can also use eye tracking for **foveated streaming**. That changes encoded stream quality rather than VRChat's render sampling. For a VRSS2 visual A/B, keep the streamer setting fixed and log it; otherwise a moving sharp region could come from the encoder rather than the NVIDIA VRSS2 path.

The common NVIDIA provider currently accepts normalized stereo UDP on localhost port 5556, takes projection geometry from OpenVR, and refuses unaudited NVIDIA driver images. With the audited HMD test branch enabled, it uses a fixed local routing key instead of requiring an OpenVR EDID. This is an output boundary; implementing a gaze input does **not** remove the driver/HMD validation requirements.

OpenVR EDID is a separate gate only on the ordinary NVIDIA consumer branch. OpenVR exposes the EDID vendor and product as tracked-device properties; Valve's driver API says properties are supplied by the device driver, and its virtual-display example explicitly covers wireless transmission. Thus lack of a physical panel EDID does not by itself prove that these OpenVR properties are absent. On the audited HMD test branch, the common path now uses `0xFEEE:0x0001` as a local provider/consumer routing key for every HMD. The connected HMD still supplies its projection/pose, and the protected launcher rechecks that geometry and a fingerprint when available. Missing EDID or serial no longer blocks the routing-key selection. A manual `VRSS_HMD_ID_CANDIDATE=vendor:product` override (decimal 1..65535) remains available for controlled research. Steam Frame's verified 596.02 path uses a different fixed session key under an owned worker and temporary profile transaction. The common fixed key has passed local exporter/provider-check and launcher-fixture tests; live VRChat rendering under that key is not yet verified.

On the audited NVIDIA 610.88 image, the local UMD trace in `work/dfr-research/nvwgf2umx-vrss-ghidra-20261023/REPORT.md` found a separate consumer-side decision: its ordinary branch copies vendor/product from the active display table, while the enabled HMD-test branch reads `TEST_VENDOR_ID` and `TEST_PRODUCT_ID` from the VRChat process. Therefore an OpenVR property alone cannot be assumed to satisfy NVIDIA's ordinary consumer branch, particularly for a virtual display. The candidate launcher uses only the observed test branch; this behavior has not been established for other driver versions.

Earlier owned-process testing registered a synthetic identity, but that only proved NVIDIA registration. In a subsequent protected VRChat A/B on this Dream Air, the official provider kept its real `0xD242:0x1019` identity while the game's NVIDIA test branch was launched once with a different synthetic identity and once with the matching real identity. The provider handshake was signaled in 81/81 samples in both runs; the consumer notification was 0/81 with the mismatched ID and 81/81 with the matching ID. Both runs had EAC session success, MSAA x4 and the same VR TestRoom. The A/B report was retained outside the public source checkout. Thus changing only the game's ID does not connect to a provider registered under another ID. A candidate is not a compatibility fix until the *same* identity is accepted on both sides, provider telemetry shows accepted frames, and a headset Force/Off image comparison confirms rendering. Do not automatically substitute another headset's ID.

## Additional PC gaze sources to implement

The source adapter should deliver independent left/right rays or explicit combined-gaze provenance, a sample timestamp or monotonically increasing frame number, per-eye validity, and a device ID. It must stop forwarding on stale/invalid data and convert the headset coordinate system through the current SteamVR per-eye projection. The Tuner's existing calibration profiles can then store headset-specific offsets and gains. Do not silently combine two active sources (for example, VIVE Streaming OSC and a VRCFT module).

1. **VIVE Focus Vision and Pro Eye:** The experimental VIVE bridge (`vive-streaming-gaze-bridge/Program.cs` in the source checkout) reads the installed `VS_PC_SDK.dll` for Streaming or `SRanipal.dll` for Pro Eye, rejects invalid/stale eye frames and projects each eye using exported OpenVR geometry. The portable build exposes separate Tuner choices. The vendor runtime and DLL are never bundled; set `VRSS_VIVE_SDK_DLL` to the full installed DLL path if it is not found in the default VIVE directory. Pro Eye requires SRanipal eye calibration. This is a *build and synthetic-data result*, not a live HMD or VRChat result. Focus 3 and XR Elite need their respective eye-tracking accessories.
2. **Varjo:** The Native SDK bridge (`varjo-gaze-bridge/bridge.cpp` in the source checkout) uses `varjo_GazeInit` and `varjo_GetGazeArray`, checks per-eye status and frame sequence, then emits normalized stereo UDP. It was built with SDK 4.16.0 and passed a synthetic projection test. Its executable is included in the portable ZIP; Varjo's runtime DLL is not. The beta.5 executable reloads horizontal/vertical gains and per-eye angle offsets every 250 ms, and observes the input stop file. It is built with the static C++ runtime. SDK compilation and synthetic projection tests passed; live calibration, concurrent face-tracking use and VRChat rendering still need Varjo hardware validation.
3. **PICO:** The BridgeSplit gaze probe (`pico-gaze-probe/Program.cs` in the source checkout) validates the documented 83-byte native-eye `E` packet and prints each eye's validity/vector. Its synthetic parser test passes, but it does not feed NVIDIA. PicoFacialBridge is single-client on UDP 9030: a second direct client would interrupt avatar tracking. The probe now requires explicit `--exclusive-test` and refuses to start when VRCFaceTracking is running. A relay or coordinated VRCFT-module change is required for simultaneous use. Legacy PICO Connect eye-look expressions are not the same as measured binocular gaze. The ordinary PICO 4 has no built-in eye tracker.

All three can potentially feed the same NVIDIA common-provider boundary. **None is verified to activate VRSS2 in VRChat** on its own. The validation sequence is: live source samples with headset worn → concurrent PC VRChat source read → NVIDIA provider receives fresh gaze → in-headset Force-versus-Off rendered-region comparison with stable resolution/MSAA. A Tuner source selection or a running bridge process alone does not establish that tracking works.

The `steamvr-gaze-probe` is deliberately read-only. Build with `steamvr-gaze-probe/build.ps1` and run the resulting executable while SteamVR is already open. It prints `bActive`, `bValid`, `bTracked` and gaze ray coordinates for five seconds. It never launches SteamVR or VRChat and does not send gaze to NVIDIA. On this machine it returned `init=121` with SteamVR stopped and `init=208` (HMD display absent) with Pimax runtime stopped. After starting Pimax and SteamVR normally, action registration and all 50 API calls succeeded (`update_error=0`, `gaze_error=0`), but every sample was `active=valid=tracked=0` while the headset was not being worn. Thus the API access path works as a background process, but live eye values and concurrent VRChat operation remain unverified.

The `virtual-desktop-gaze-probe` maps `VirtualDesktop.BodyState` read-only according to the MIT-licensed Virtual Desktop VRCFT module's `FaceState` layout. It does not consume the module's event or send any samples. Build with `virtual-desktop-gaze-probe/build.ps1`. Without a Virtual Desktop streamer it returned `VD_SHARED_STATE_UNAVAILABLE error=2`, as expected. A later live streamer version must verify the layout and update freshness before forwarding any gaze; the shared struct itself has no sequence or timestamp.
